# Rendezvous · 会合

## North Star

> 让等待保持安静，让变化带回行动。

Agent 将外部等待交给运行时，在有意义的变化到来时恢复执行，使推理用于推进任务。
本 Skill 定义等待交接与恢复合同；实际观察、调度和消息投递由当前环境提供。

## 确定等待事项

从用户请求、会话和权威工具取得：

- 要恢复的会话，以及本次委托是一次等待还是持续跟进。
- 外部工作的身份、状态来源和唤醒条件；必要时包含版本或重跑次数。
- 恢复后的下一步，以及已有的停止条件或期限。

复用已有会话、任务和 run 身份。自然语言能明确表达时，无需新增 ID 或固定消息协议。
只有缺失信息影响目标或授权时才询问用户。读取或设计请求不启动监控；已有的等待与唤醒授权
可直接使用。恢复指令沿用原任务的范围，不额外授权修改代码、重派任务或重跑外部操作。

## 交出等待

如果原生 wait 支持目标且等待期间无需重复推理，直接使用该能力。需要跨 turn 等待时，选择能在
当前 turn 结束后继续负责等待的现有机制。优先使用原生订阅或确定性观察接口；没有这些能力时，
可采用下述 heartbeat 路径。不要为本次等待临时搭建常驻脚本或通用调度框架。

跨 turn 交接按以下顺序进行：

1. 复用同一会话和委托已有的监控，登记具体等待对象、唤醒条件和恢复目标。
2. 确认机制已经接管，再读取外部当前状态，覆盖工作在登记前或登记期间完成的情况。
3. 条件尚未满足时，让执行会话结束当前 turn。等待由已登记的机制继续处理。

如果无法建立跨 turn 的等待，报告“未接管”及缺少的能力。不要用持续的模型查询循环代替交接。
调度配置已存在，只能证明已登记；实际定时执行仍需运行证据。

## 按变化恢复

观察端从外部权威接口读取当前状态。未变化的状态和普通日志不触发执行会话；完成、失败、
取消或约定的决策条件才触发恢复。查询失败表示状态未知，按所选机制退避重查。

发送前核对等待事项仍有效。通知包含外部工作身份、观察到的变化和恢复后的下一步。
要求执行会话重新核对当前结果与版本，再继续原任务。外部工作结束不代表任务验收通过。

发送被接受后，记录本次投递，并在后续检查中确认接手。消息暂时不可见时保持“已发送，
接手未确认”，不因消息暂时不可见而重发。发送结果不明时先核对；无法确认时报告不确定性。
重复或过时的通知不能重复启动原操作。不要声称这些检查提供了严格的 exactly-once 保证。

一次等待在执行会话接手或等待被取消后结束。持续跟进期间，暂时没有外部等待只降低观察频率；
在没有主动登记下一次等待的能力时，仍需保留低频发现。委托完成、被取消或达到停止条件后，
停用对应监控，不影响其他委托。

## 当前可用路径：ChatGPT + heartbeat

这是可用的原型路径，尚不具备无推理成本的订阅或严格的投递保证：

- 用 Codex App 的 `read_thread` 读取目标 ChatGPT 会话，用 `send_message_to_thread` 发送恢复指令。
  先确认这些能力支持目标会话；不要把仅支持 Codex 任务的 `wait_threads` 用作 ChatGPT 等待器。
- 外部工作使用其所属系统的读取接口。例如 CI 使用仓库、run ID 和必要的 attempt 查询 GitHub，
  不把聊天中的旧状态当作当前结果。
- 用现有 `automation_update` 创建或更新当前调度任务的 heartbeat，默认每 5 分钟检查。
  每轮只读取识别有效等待所需的消息和外部状态；没有变化时保持安静。
- heartbeat 指令携带上述等待上下文及已知投递情况，使后续执行能继续处理同一事项。
  不要只把恢复所需信息留在当前调用的临时变量中。

此路径让执行会话停止轮询，但观察端每轮仍可能调用模型，且发现变化存在检查间隔延迟。
目前只能按实际工具结果报告登记、投递和接手；恢复能力、漏通知风险及成本改善需在目标环境验证。

## 交付与验证

初次交接报告：等待对象、采用的机制、是否已登记、检查间隔及停止条件。
恢复或结束时报告：触发变化、投递结果、接手证据、剩余监控和未验证项。

验证重点是：等待期间减少了哪些无效模型调用；登记期间完成的工作是否仍被发现；通知延迟、
重复或过时时是否正确处理；会话是否继续了原任务。一次 live 成功只证明该环境和该路径。
机制的局限按观察结果记录，不把 North Star 写成当前已实现的保证。
