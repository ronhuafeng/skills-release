# Apply

## 目标

完整修复用户已确认且可精确识别的 findings，并删除它们留下的失效实现和表述。

## 契约

- findings 和用户指定范围在本次执行中固定；不重新发起全仓审查或顺带清理。
- 修改前确认每项 finding 的关键证据在当前工作树中仍然成立。
- 保留仍被调用，或由当前契约、现实数据和可重复运行结果明确要求的行为。
- 删除被替代能力时，不保留 deprecated API、兼容 facade、adapter、fallback、
  双路径或只用于维持旧形状的代码。
- 同步删除相关的失效测试、fixture 和文档表述；不要用历史说明继续传播已经删除的
  runtime 模型。
- 删除仅用于断言旧接口、旧输入形状或已移除 runtime 模型的测试；保留能够证明当前
  公开行为、唯一执行路径的关键不变量和已修复失败模式的回归测试。不得仅因类型系统
  覆盖结构约束而删除具有独立行为价值的测试。
- 保留所有无关工作树修改。

## 流程

1. 检查当前工作树、findings 涉及的定义、调用方、契约、测试和文档。修改前复述已
   确认 findings 的固定清单并保留 review ID；如果原报告没有 ID，为每项分配本次
   apply 内唯一的 ID。不要创建独立 findings 数据库或进度账本，实施状态以当前工作树
   和 diff 为准。
2. 如果证据仍成立，按照 finding 的目标状态保留唯一当前路径，或完整删除不再存在的
   能力；删除被替代结构并更新调用方，不要增加新的兼容层或迁移框架。
3. 同步更新受影响的测试、fixture 和文档，使其只描述修改后的现实。
4. 检索旧名称、旧输入形状、旧 schema、adapter、fallback、并行实现、死代码和
   冲突表述。逐项核对残留是否仍由当前契约要求，不能仅凭命中名称继续删除。
5. 从仓库文档、CI 或现有工具中发现并运行与修改相称的测试、静态检查、构建和格式
   检查。条件允许时，使用真实数据执行只读 live validation。
6. 检查完整 diff，按 ID 确认每项 finding 的实施状态和验证状态、没有引入替代兼容路径，
   并且无关修改未被纳入。

如果发现 finding 已失效、仍有现实消费者、公开契约无法确定，或修复必须扩大用户
授权范围，停止对应修改并报告具体证据；不要猜测或静默保留半套实现。

只有在失败可重复，并且有证据排除本次 diff 对测试、被测代码、配置、构建入口和依赖
路径的影响时，才能报告验证失败与本次修改无关。优先使用不包含本次修改时同样失败的
基线证据；证据不足时标记为 `unresolved`，不得称为既有问题。

## 完成条件

- 每项已确认 finding 均已修复，或因新证据明确说明无法安全实施；
- 被删除能力在代码、测试和当前文档中没有失效残留；
- 必须保留的行为具有当前调用关系或现实契约证据；
- 适用验证通过；无法运行或仍为 `unresolved` 的验证明确标记为未验证，对应 finding
  不得报告为已验证关闭；
- 没有修改无关用户工作。

最终按 ID 简要报告每项 finding 的实施状态、验证状态、删除与保留证据和明确限制。
