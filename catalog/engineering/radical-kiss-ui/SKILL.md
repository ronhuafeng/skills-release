# Radical KISS for Product UI

把 Radical KISS 理解为：删除偶然复杂度和故障路径，让操作者用最少认知负担完成完整任务。精简界面，不缩减产品边界。

## 工作步骤

### 1. 固定产品边界

读取需求、Issue、现有产品文档、领域词汇、权限规则、代码和真实界面。确定：

- 操作者是谁，要完成什么任务；
- 哪些能力属于正式系统边界；
- 哪些信息改变判断，哪些动作改变状态；
- 服务端、浏览器和外部系统分别拥有什么权威；
- 哪些约束属于当前产品，哪些只是参考产品的局部取舍。

事实优先从仓库和运行中产品取得；只有客户权力边界、风险偏好或不可逆产品边界无法由证据确定时才询问用户。

完成条件：能用一段话说清操作者、任务闭环、必需能力、权威边界和不可照搬的参考约束。

### 2. 追踪纵向旅程

为每项用户能力追踪完整链路：

```text
入口 → 找到对象 → 理解状态与证据 → 执行获授权动作 → 看见结果 → 恢复或继续
```

逐项核对稳定 URL、导航、具名对象、权限、空状态、失败状态、busy 状态、结果反馈和审计入口。把需要内部 ID、原始 JSON、API 工具或后台知识才能跨过的环节标为旅程断点。

完成条件：每项范围内能力都有可观察的入口、证据、动作、结果和恢复路径，所有断点均已列出。

### 3. 建立单一权威

让服务端拥有业务决策和最小页面投影：

- read model 返回人类可读名称、状态、责任、证据摘要、允许动作和稳定 Web href；
- command 在服务端校验权限、eligibility 和当前状态；对可重试、非幂等或高影响 mutation 明确去重与重放策略；
- 浏览器呈现 proposal/allowed actions，收集用户意图并提交命令；
- 原始 JSON、metadata 和内部标识进入明确标注、权限受控的次级诊断入口；
- shell 只依赖最小导航与身份投影，业务页面独立读取自身模型。

选择最少运行阶段。只读或读取为主的页面默认由服务端返回可独立使用的首屏内容，JavaScript 增强 mutation、轮询、预取和局部刷新。必须依赖客户端运行时的产品，应明确启动、离线、失败和恢复边界。

完成条件：每条业务规则、名称解析和 allowed action 都只有一个权威实现；客户端状态只保留交互所需最小集合。

### 4. 压缩认知负担

按操作价值组织信息：

1. 当前任务与主要动作；
2. 异常、风险和待处理事项；
3. 会改变判断的状态与证据；
4. 正常汇总与次级详情；
5. 原始诊断信息。

保留直接描述数据或操作的标题、标签和辅助说明。合并重复标题、正常成功提示、零值状态墙、装饰性文案、无行为控件和同一事实的多种格式。通过折叠、分页、截断提示和详情页处理信息量，同时保持完整内容可达。

完成条件：首屏能回答“我在哪里、什么需要处理、下一步是什么”；每个可见元素都支持判断、操作、定位或恢复。

### 5. 选择交付分支

只执行用户授权的分支。

在浏览器验证可能改变外部状态前，确认目标是安全测试环境、测试数据可恢复，且该副作用已获明确授权。条件不满足时保留现状，停止 mutation 验证，并说明缺少的证据和最小解锁条件。

#### 设计

产出：

- 信息架构与稳定 URL；
- 页面级任务、read model 和 command 边界；
- 导航、主要动作和渐进披露层级；
- loading、empty、busy、success、failure、partial unavailable 状态矩阵；
- 桌面与窄屏行为、键盘和辅助技术语义；
- 可验证的验收标准。

用最小有用的 wireframe、状态表或流程图表达复杂关系；简单页面直接使用文字。

完成条件：实现者无需自行发明产品规则、失败语义或响应式行为。

#### 审查

按用户授权范围检查可用的需求、代码、API 契约和真实浏览器行为；证据可用且验证安全时，联合检查这些表面。覆盖范围内的桌面、窄屏、键盘操作、主要 mutation、失败状态和稳定深链接；适用时检查禁用 JavaScript 或脚本失败场景。把缺失或无法安全取得的证据标为“未验证”及其影响，不把证据缺失本身当作产品 finding。

按用户影响排序 findings：

- P0：安全、数据或核心系统完整性风险；
- P1：核心旅程不可完成、误导决策或可产生错误状态；
- P2：显著可用性、可访问性、故障隔离或维护风险；
- P3：局部一致性、视觉或低风险技术债。

每项 finding 给出证据位置、可复现场景、用户影响、违反的原则和目标行为。已有测试通过只能证明其覆盖范围，不能替代真实浏览器证据。

完成条件：范围内每条核心旅程和适用验收门都已有通过证据、明确 finding 或标注影响的未验证项。

#### 重构

先固定当前用户行为和失败语义，再以最小纵向切片收敛边界：

1. 建立或补充能暴露问题的自动化/浏览器验收；
2. 将具名 read model、策略和 allowed actions 收回服务端；
3. 统一 typed query/command lifecycle；
4. 精简页面结构与客户端状态；
5. 验证桌面、窄屏、权限、重复提交和失败恢复；
6. 删除被替代的路径和重复契约。

完成条件：产品能力保持完整，权威实现收敛，目标验收通过，旧路径已移除。

## 验收门

在设计、审查或重构结束前逐项核对：

- **任务完整**：用户能从稳定入口完成整条旅程，不需要内部 ID、原始 JSON 或外部 API 工具。
- **界面精简**：删除的是偶然复杂度；正式系统要求的能力仍然可达。
- **服务端权威**：权限、eligibility、策略、名称和 allowed actions 不在浏览器形成第二实现。
- **可恢复 mutation**：按副作用和重试风险选择幂等、版本校验或去重机制；可重试的非幂等、高影响操作使用稳定 operation/idempotency key；提交期间阻止重复动作；失败后状态明确且可安全重试。
- **URL 即状态**：持久、可分享且非敏感的页面、对象、筛选和导航状态可复制、刷新、前进和后退；敏感或短暂状态不进入 URL；当前位置使用 active state 与 `aria-current` 表达。
- **渐进披露**：主界面使用领域语言；原始诊断信息位于次级入口且权限明确。
- **注意力诚实**：“需要关注”只包含异常、风险或待处理事项，正常状态进入紧凑摘要。
- **状态完备**：loading、empty、busy、success、failure 和 partial unavailable 有确定语义，不以永久 skeleton 代替内容。
- **故障隔离**：当前页面只依赖自身所需模型；无关模块故障不扩大阻断范围。
- **无障碍与响应式**：控件有持久标签和可访问名称；状态不只依赖颜色；窄屏导航可辨识；宽内容可聚焦和滚动。
- **有界输出**：参数、截断、分页、数值格式、查询量、安全头和错误响应都有明确上界及测试证据。
- **性能服务正确性**：首屏读取最小必要数据；预取和缓存只负责提速，不成为正确性前提。

## 报告方式

先给出结论，再给证据和下一步。设计报告明确产品决策与未决客户问题；审查报告按优先级列 findings；重构报告说明用户可见变化、权威边界变化和验证结果。

把参考产品的原则与其局部非目标分开陈述。只有当前仓库授权文档变更且结论具有长期价值时，才把稳定结论写入最接近的规范、领域文档或 ADR，并同步受影响文档。
