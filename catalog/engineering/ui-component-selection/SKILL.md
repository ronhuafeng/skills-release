# UI 组件选型

从用户要完成的动作出发，选择组件及其组合。使用户能找到下一步、理解操作后果，并在判断时保留所需上下文。

## 范围与项目约束

- 遵循项目已有组件库、设计 token 和交互规范。组件名称是候选，不是更换技术栈的理由。
- 按当前请求执行：审查交付问题和建议；实现交付实际修改。选型本身不授权改动业务规则、权限或后端。
- 保留用户需要的能力与重要条件。通过调整展示位置和信息层级降低负担。
- 领域组件可以组合标准组件；其职责应是一个清楚的用户任务，而不是另一套通用视觉体系。

## 选型流程

### 1. 查明真实任务和现有组件

读取适用的仓库说明、设计规范，以及相关页面、组件和状态管理代码。查明已安装的组件及版本；只调查当前区域需要的部分。

用一行说明每个待调整区域：

> 用户处理的对象 → 要完成的动作 → 状态变化；何时生效；必须同时可见的信息；内容规模和设备约束。

例如：选择参与审核的文件 → 修改选中集合 → 提交时生效；文件名与选用状态同时可见；多文件、长文件名、支持手机。

页面名称和文字关键词不能独立决定组件。已有 UI 的结构也只是一个候选方案。关键事实不足时，指出具体未知项；只在它会改变操作后果或业务范围时请求澄清。

### 2. 根据交互语义选择

下表提供默认候选。按项目实际 API 和任务约束调整。

| 用户意图 | 默认候选 | 关键判断 |
| --- | --- | --- |
| 到达另一个位置或页面 | Link | 保留导航、打开新标签页等链接行为。 |
| 执行命令或提交 | Button | 动作、提交时机和结果清楚；处理中防止重复执行。 |
| 独立选用某项或选择多项 | Checkbox | 表达集合成员或独立布尔选择；是否立即生效由任务决定。 |
| 从互斥选项中选择一个 | RadioGroup、Select、可搜索 Combobox | 需要比较且数量少时直接展示；数量或检索需求增加时收拢或支持搜索。 |
| 开启或关闭一个持续设置 | Switch | 用户将其理解为某项功能的开关；生效时机要明确。 |
| 切换操作或显示模式的按下状态 | Toggle、ToggleGroup | 表达 pressed 状态，例如格式工具；业务选项仍按选择语义判断。 |
| 阅读可以互斥显示的平级内容 | Tabs | 切换不会妨碍比较或丢失关键上下文；其职责是切换内容。 |
| 展开当前对象的次要操作 | DropdownMenu | 用于命令；数据值选择仍使用选择控件。 |
| 完成一个有明确结束点的局部任务 | Dialog、Sheet、Drawer | 内容与空间合适，关闭后能返回原上下文；需长期对照的信息优先内联。 |
| 比较原件、证据与判断 | 分栏布局、Resizable、ScrollArea | 让必要信息同时可见；窄屏切换时保留选择、阅读位置和编辑状态。 |
| 按需查看附属信息 | Tooltip、Popover、Collapsible | 关键判断条件和完成任务必需的信息保持可见；Tooltip 内容也能通过键盘到达。 |
| 展示状态、进度或需要处理的问题 | 文本、Badge、Progress、Alert | 呈现真实状态；收到、已保存、已解决和可批准分别表达。 |

不要把“立即生效”当作区分 Checkbox、Switch 和 Toggle 的唯一条件。先确定它表达的是选择、设置还是操作状态。

明显的选型直接决定。有实际取舍时，比较最有可能的候选，依据包括：可发现性、点击与往返次数、记忆负担、内容容纳能力及误操作后果。仅以“更现代”或“更好看”无法证明选择正确。

### 3. 组合成最小、完整的工作区域

- 组织顺序遵循用户的判断和操作顺序。主动作突出，次要动作靠近其对象；批量操作随选中集合出现。
- 使用 Table 或 List 服务扫描与比较，使用 Card 表达独立内容单元。长文件名、数量和状态应能被识别；需要截断时提供完整内容的访问方式。
- 每层可见边框、背景、缩进和标题都应表达一个实际分组。可通过同一平面上的间距、对齐和分隔线表达关系。
- DOM 包装数量不等于视觉嵌套问题。检查重复边界、重复标题、重复滚动区和过长的阅读路径；保留实现布局或组件行为所需的包装。
- 标签、帮助文字和图标各承担一个用途。熟悉的操作可用图标；含义需要推测时保留短文字。图标按钮提供可访问名称。
- 桌面与手机可以使用不同组合，保持相同的业务含义。响应式调整应保留用户已选对象和未提交内容。

### 4. 核对组件行为与结果

从本地实现、类型和已安装版本确认 API。遇到不确定的行为，再查对应版本的官方文档。保留组件库的键盘、焦点、选中和关闭行为，避免样式把一种控件伪装成另一种。

对调整区域检查有代表性的真实内容和状态：长文本、多项数据、空状态、选中、禁用、处理中、成功及失败。检查用户能否知道动作是否已生效，以及下一步在哪里。

代码审查、类型检查与实际交互检查提供不同证据。按当前任务使用可用的验证方式；没有运行的交互明确标为未验证。组件名称、截图或构建通过都不能单独证明选型正确。

## 交付与完成条件

按问题简洁报告：

> 区域与用户任务 → 当前不匹配之处 → 推荐或已采用的组件组合 → 理由及验证情况。

审查完成时，每个发现应有具体位置和可执行建议。实现完成时，调整区域应使用真实存在的组件 API，保留所需业务能力，并说明未验证的交互。只解释会影响用户操作的取舍，无需为明显的选型逐项写报告。
